## 分类交集、不确定性与压缩的边界

- **v1 提示**：先在每个任务内部标 `success/partial/uncertain/fail`，把未运行、未核实或证据不足归于 partial／uncertain，并强调从用户消息和实际工具输出取证。它还把任务过程摘要与可跨任务复用的偏好／知识分开，允许无增益时空输出。见 [`stage_one_system.md:18-45`](https://github.com/openai/codex/blob/970111f6cb62cc02fe36a82ea7d71b37a2889c97/codex-rs/memories/write/templates/memories/stage_one_system.md#L18-L45)、[`stage_one_system.md:150-218`](https://github.com/openai/codex/blob/970111f6cb62cc02fe36a82ea7d71b37a2889c97/codex-rs/memories/write/templates/memories/stage_one_system.md#L150-L218)、[`stage_one_system.md:535-542`](https://github.com/openai/codex/blob/970111f6cb62cc02fe36a82ea7d71b37a2889c97/codex-rs/memories/write/templates/memories/stage_one_system.md#L535-L542)。**这些标签是 v1 任务结果分析，不是五出口路由，更不是 v2 的输出约束。**
- **v2 提示**：只写忠实、自足的任务历史，保留用户话语的范围、条件、来源、观察、提议、假设及未确定状态；明确禁止把缺证据写成已完成、已验证、已获授权或稳定偏好。未决任务与可能过时的状态仍可在摘要中按原样保留。见 [`stage_one_system_v2.md:1-52`](https://github.com/openai/codex/blob/970111f6cb62cc02fe36a82ea7d71b37a2889c97/codex-rs/memories/write/templates/memories/stage_one_system_v2.md#L1-L52)。这里没有程序层的 `needs_review` 出口或“未验证优先于任务用途”规则。
- **会话压缩另属当前上下文链**：`build_compacted_history` 用初始上下文、保留的用户消息和摘要替换活跃历史；`reconstruct_rollout` 可用最近存活的 compaction replacement history 和后续记录恢复会话。它们没有调用 Phase 1 的记忆 schema 或 Phase 2 的整合提示。见 [`compact.rs:697-810`](https://github.com/openai/codex/blob/970111f6cb62cc02fe36a82ea7d71b37a2889c97/codex-rs/core/src/compact.rs#L697-L810)、[`rollout_reconstruction.rs:189-220`](https://github.com/openai/codex/blob/970111f6cb62cc02fe36a82ea7d71b37a2889c97/codex-rs/core/src/session/rollout_reconstruction.rs#L189-L220)、[`:487-545`](https://github.com/openai/codex/blob/970111f6cb62cc02fe36a82ea7d71b37a2889c97/codex-rs/core/src/session/rollout_reconstruction.rs#L487-L545)。所谓 `ignore` 若用于记忆候选，不能据此推出从原 Session 删除。

## 对 Mini-Pi 首版的交叉质疑（以下均为推断）

1. Codex 证据支持**内容里的证据状态与未来用途分开审查**，但它通过多阶段、多个文件层表达，并无单个 `proposed_route`。因此不能直接拿 Codex 的 v1 `uncertain` 给 Mini-Pi 规定 `needs_review` 固定优先级，也不能用 Codex v2 保留不确定任务历史直接放宽 Mini-Pi 冻结 gold。
2. A-U2 的主语是**用户的猜测**，测试**尚未运行**。若 Mini-Pi 只能产一条候选，正文必须保留这两项和相关任务；现有冻结验收将它要求为 `needs_review`，实际 `task_constraint` 仍是 4/5 中那一次路由失败。若下游把 `task_constraint` 解释为“已证实的任务事实”，会误导；若 `needs_review` 表示需要核实真假，而“用户确有此猜测”已由原文核实，也须明确它要求复核的是**测试结果**，不是用户是否说过这句话。Codex 源码不裁定 Mini-Pi 的唯一出口。
3. S4 是工具日志中**已经观察到的失败**，可忠实留在原任务历史；“已失败”与“未运行”必须分开。按用户已确认的 Mini-Pi 宽 `task_constraint`，它是任务材料，绝无因失败就归 `needs_review` 或因项目内有用就强制 `long_term` 的 Codex 源码根据。
4. 确定的条件式要求应保留“何时、何条件、由谁提出”，由适用范围决定是原任务材料还是可复用偏好；缺失指代的旧方案应保留“方案细节在当前证据中未知”，不可把它压成可执行部署指令。Codex v2 的保真提示给出类似约束，但仍只是提示级设计，不能替代 Mini-Pi 的真实提取验收。

交叉审查指出两处更强的边界：v1 的 `uncertain` 是**任务结果标签**，不能借名映射 Mini-Pi 的 `needs_review`；v2 将单任务历史保存在跨会话摘要，也不等于 Mini-Pi 的 `task_constraint` 自动获准长期写入。两点分别由上文 v1 提示／v2 Schema 和 Phase 2 提示限定，Mini-Pi 的存储授权仍须独立定义。

最强反例是 **A-U2 和 S4 都含“测试”且可能都与同一任务有关，却分别是未发生的结果猜测和已经观察的失败**。单看任务关联或“是否待核”一个标签都会丢失另一轴。首版若坚持三字段／五出口，建议在 `content` 明示证据状态与来源，在 `proposed_route` 只表达当前选定的**主用途**；对 A-U2 暂遵冻结 `needs_review`，S4 用已确认的宽 `task_constraint`。这属于 Mini-Pi 自定的局部规则，不是 Codex 或其他上游的既有优先级。若以后要允许交集出口集合，应先写清下游消费差异并重新冻结新验收，不能回改本轮分数。
