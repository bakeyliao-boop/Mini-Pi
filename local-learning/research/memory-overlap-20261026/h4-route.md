## H4 可确认的事实

- [冻结 H4](../../../examples/fixtures/memory_overlap_acceptance_v21.json) 的唯一原文是“预发环境的限流参数继续沿用会议里那一版。”要求保留沿用意图及本条材料缺少具体参数/所指细节，单出口为 `needs_review`。这**不能**推出会议从未确定配置。
- [实际 request-04](../../../local-learning/evidence/memw-overlap-v21-live-20261026-01/request-04.json) 仅把这一条 `role/recorded_at/text` 交给模型，无会议记录、配置文件、版本 ID 或前序消息。返回 `stop` 的 JSON 合格；`content` 只复述沿用意图，`proposed_route=task_constraint`，`reason` 说“未涉及猜测或需核验的冲突”。没有编造参数数值，却遗漏了执行所需配置尚不能从本次输入确定的限定。
- [当前提示](../../../mini_pi/memory/extraction_client.py) 第 24–80 行已经规定单条提取、`content` 保真以及“缺少前文而无法解析执行所需的方案、步骤或配置时，应 `needs_review`”。第 119–150 行的请求构造与类说明确认不会自动补充跨消息前文。[路由代码](../../../mini_pi/memory/selection.py) 的 `route_candidates` 仅按模型标签归组，不核对语义、查询会议纪要或阻止下游误用。
- [冻结结果](../../../local-learning/evidence/memw-overlap-v21-live-20261026-01/acceptance.json) 为技术 6/6、正文 6/7、路由 6/7、严格 6/7、整案 5/6，仍未通过。旧 S3 的 4/5 和 v2 离线 8/9 是不同证据。

H4 的**用户意图明确**：预发环境沿用某个既有版本；不明确的是**哪个可执行的参数版本**。它是未解的外部工件指代，不是“用户猜测会议是否开过”或“配置值已被证明为假”。提示中的“缺少前文”容易被狭义理解为聊天前文缺失，未充分覆盖会议纪要、附件、配置中心等外部所指；这只是对失败机制的合理推断，单次输出不能证明模型为何忽略第 3 条。`reason` 的“没有猜测/冲突”显示其将显式真假冲突当作复核条件，至少没有在输出中处理配置指向缺口。

因此 H4 的 `needs_review` 是 **Mini-Pi 当前冻结的首要后续处理契约**，不是四仓给出的优先级。原 Session 保留一句原话、压缩摘要复述意图、长期记忆写入、向当前模型 Context 注入、找回会议参数是不同动作；提取出一句忠实候选不会自动完成后四件事。

## 最小判准与反例

建议把“缺少前文”精确解释为：**本次可信输入既未给出执行所需内容，也未给出能在指定时点确定它的引用或选择规则**。先判断能否确定所指，或用户是否已明确要求先取证再行动；不要按“那版/之前”或“没在正文写数值”机械分类。下面是未来判准建议，尚未改代码或复验：

| 原文形态 | 正文应保留 | 首要处理 |
| --- | --- | --- |
| H4：“沿用会议里那一版”，只给这条 Source | 沿用意图；当前材料没有具体参数，也没有唯一版本标识 | `needs_review`：澄清是哪版/从何取得；不得填造 QPS 等值。 |
| “沿用配置中心 `preprod/rate-limit` 的不可变版本 `rev42`” | 指针和沿用意图；参数值尚未读取 | 可为 `task_constraint`：指代已可唯一定位；真正执行仍须读取、核对 revision、权限与参数，不能声称已获值。若该指针并不唯一或不可取，仍待核对。 |
| “执行时取指定仓库 `main` 的 HEAD 中指定限流文件，核对后应用” | 动态选择时点、仓库/分支/路径及先核对的条件；没有预言未来值 | 可为 `task_constraint`：版本会变化，但选择规则明确；执行时须解析并固定当时 SHA、读值、核权限。不能因为没有不可变版本号就机械待核。 |
| “先查指定会议纪要第 3 节的参数，确认后再改” | 先查后改的明确条件，当前尚未取得值 | 可为 `task_constraint`：当前任务本身明确要求先检索；不能把该句改写成立即按未知数值修改。若纪要无法定位，后续应报告阻塞。 |
| “沿用会议版：QPS 200、突发 50” | 具体给定值、环境、沿用要求 | `task_constraint`：同条已给执行所需内容；执行许可和现行有效性仍独立检查。 |
| “先不要改限流；参数沿用会议那版”且版次未知 | 独立的暂停修改要求；另有未解的版次 | 可拆成 `task_constraint` 的明确暂停要求和 `needs_review` 的参数指代；不因后一部分未知抹掉前一部分。 |
| “我猜会议版 QPS 200，尚未查看纪要” | 猜测与未核对来源 | `needs_review`：这是数值真假待核，与 H4 的版本指向缺失又不同。 |

对于表中的精确指针或明确选择规则，**尚未验证能否访问**本身不宜自动改为 `needs_review`：很多明确任务要求引用尚未读取的文件或配置；`task_constraint` 仅记录原任务要求，不表示指针已打开、值已核实、已经获审批或可立即执行。固定身份、可获取性、审批状态是三种不同判断；“该版本已获审批”若只是未经核对的转述，应单独保留其来源/待核状态，不随确定的使用要求一起当作已证实。若本条 Source 已明确指针失效、无权限或版本有歧义，才有当前可见的定位阻塞；若后来检索失败，则在后续任务阶段呈现失败并求核对，不追称提取时已经知道失败。这个区别来自 Mini-Pi 的单出口含义和执行门禁设计，**不是 Codex/Claude 源码规定**。

更强的反驳是：在另一套契约里，`task_constraint` 只表示“记录用户确实要求沿用会议版”，且消费方强制拦下未取到的参数，此路由也可能自洽。但本版提示把路由定义为**首要后续处理**，H4 冻结 gold 唯一为 `needs_review`；事后改 gold 会回算真实 6/7。更重要的是，当前 `route_candidates` 只归组，MEM-04 消费门禁尚未实现，不能把“消费方会安全拦截”当作当前行为证据。若将来正式变更路由契约，必须先写清 `needs_review` 与 `task_constraint` 的不同消费动作、预先版本化新 fixture，再运行新授权的验证；这不改变本轮失败。
