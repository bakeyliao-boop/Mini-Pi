## MEM-03 最小向量检索契约（2026-10-22 用户确认）

本节替代此前未完成的关键词命中数计分与多级排序计划；下方早期设计/测试条目保留为历史，不再作为当前验收标准。MEM-03 的目标是接收自然语言 query，在可信 Scope 内返回语义相关且适用的原始记忆证据，不要求调用方枚举属性 key。运行/学习顺序仍为 MEM-03 → MEM-W → MEM-04。

### 参考源码与裁剪依据

红熊开源产品 MemoryBear 固定参考提交 a2960b3b6313704448d6f7ab0243aefede802238（静态审阅，未部署运行）：service_models.py 的自然语言 question 与 MemoryContext.end_user_id 分离；read_services/search_engine/content_search.py:170–184 生成 query embedding 并传入存储检索；search_policy.py:10–33 按用户及软删除状态过滤；hybrid_search:520–628 实际并行关键词和向量召回，可融合或模型重排。不能将该路径说成纯向量检索，也不据这里字段存在声称具备我们的项目/适用时间/CAS契约。引用仓库：https://github.com/SuanmoSuanyangTechnology/MemoryBear/tree/a2960b3b6313704448d6f7ab0243aefede802238 。固定 Pi 7f9e119 仍是原Agent/Session行为基准；该版本不提供此结构化跨会话语义记忆检索。

借鉴自然语言查询、可信身份独立、统一embedding端口、过滤与相关性分开及结果保留来源的边界。第一版不照搬混合检索、模型重排、图谱、异步索引、Redis、Elasticsearch或独立向量库。也不复制产品README准确率、延迟、默认阈值作为验收指标。

### 完整流程与输入输出

输入：query、可信 scope、问题时间 at、场景 conditions、注入的固定 Embedder，以及显式 top_k/min_score。query 非空；top_k 为真正正整数；min_score 为 [-1,1] 内有限实数，实际值须经模型校准后固定，不能抄0.5或用测试集反复调整。key 仍用于 MEM-01/02 系列维护，不是查询必填项；terms 不再是语义检索输入。

1. 核对参数，复用只读 SQLite 快照加载候选并核对来源。
2. 复用 is_usable 排除范围、撤回、条件与问题时间不适用条目；不把这些原文发给embedding。没有合法候选则返回空列表，零模型请求。
3. 对 query 调用 embed_query，对合法 Entry.text 原文批量调用 embed_documents；不使用 key+原文的词数计分。查询/文档方法可以按模型要求采用不同前缀，但必须属于同一兼容向量空间。
4. 核对模型规格未变、维度、向量数量和文档顺序对应、非零及有限数值，计算余弦相似度；技术失败抛明确错误，不伪装成无记忆。
5. embedding 返回后重新读取主记录，核对来源及当前状态，再调用 is_usable，剔除期间撤回或失效的条目。原候选集合以开始读取快照为准；并发新增记录在后续查询可见，不宣称检索返回后永不变化。
6. 只对仍可用记录应用 min_score，按余弦相似度降序，最后取 top_k。同分保留候选既有稳定顺序，不增加生效时间/ID的业务优先级。返回完整 Entry 与相似度；来源、版本、时间和原文不丢失，相似度不等于事实真实性。
7. MEM-04 后续负责请求前复核和 Context 预算处理；MEM-W 后续负责自动候选写入，不将embedding视为记忆价值判断。

第一版不持久化向量缓存，每次查询重算合法候选向量，用于先验收闭环；代价是重复计算、时延和费用，必须实测。若成本不可接受，另定义缓存与模型/内容失效协议后再实现，不暗中加缓存或假称已解决索引维护。embedding是额外模型调用，须保留真实异步取消传播及资源关闭证据，不能将同步线程包装或状态标签当取消保证。具体真实模型、版本、维度、预处理、阈值与适配器仍待选定和验收；未获实际结果前不得声称真实语义效果通过。

### 验收门禁

- 确定性门禁：固定向量与真实临时SQLite/JSONL核对跨用户/项目隔离、已撤回/不适用记录即使最高相似度也不得返回，源数据不发送到错误范围的模型调用；无候选零调用。
- 相关性与返回：相同/正交/相反方向和非单位向量的余弦正确；阈值边界、低分空结果、同分稳定、过滤及阈值后才取top_k；完整Entry来源版本保留。
- 维护一致性：未来v2生效前仍可取历史区间内v1；真实retract排除所有版本；在await embedding期间更新/撤回后返回前复核，不复活旧状态。
- 技术故障：错维、错误批量数量/次序协议、模型配置变化、NaN/Inf/零向量、embedding异常须明确失败；无部分成功、无意外写库，不重跑历史工具。模型返回顺序由适配器明确保证，服务若返回索引必须验证/重排，不能把向量安到错误Entry。
- 生命周期：主动取消、超时均传到实际请求并核对关闭/停止边界，记录与返回一致；不声称超出既定D12行为的硬实时保证。
- 真实语义效果：单独固定模型和小型人工标注集，使用不同的校准集与验收集；包含用词不同但含义相关、必要证据、多条支持以及不相关查询；逐例报告top_k命中、漏召回和误召回。模拟向量通过不能替代这层验收。
- 成本：查询向量与候选向量调用量、候选数量、耗时、可获得的token/费用与重试分开统计；缺项标缺失，不当零。不将产品宣传数据或一次演示写成我们的结果。

### MEM-W 范围、输入输出与分工

输入为可信调用方指定的 Scope、已经保存的原始 Session/工具来源、当前任务标识和必要时间背景。模型如参与，只提出候选，不决定可信身份，不直接改数据库。

第一层：写入选择与候选提取。区分长期用户事实/偏好、带项目版本的情景事实、待验证的程序性候选、当前任务约束，以及忽略/待核对内容。输出带 source_id、精确原文证据位置、key、kind、conditions、时间依据、证据状态和选择理由的结构化候选或分流结果。不能从消息角色、聊天形式或单次成功直接推断长期价值、世界真实性或通用技能；不能猜测省略的时间/条件。

第二层：写入计划与提交。核对来源/片段和元数据，与已存系列比较，输出新增、重复、显式更新、条件并存或待核对；通过门禁后调用 MEM-01/02。撤回意图走明确控制操作，不当新偏好入库；已撤回历史内容不可被重建或旧对话提取自动复活。当前任务约束单独传给 MEM-04 固定约束输入，不默认写成跨任务偏好。

现有 MEM-01 仅允许整条原文，MEM-W 不得暗中绕过。若一句消息包含多项内容、需要片段级候选，必须作为本单元明确子步骤：保留完整不可变 Source，校验 Draft 精确片段与提取字段的支持关系，更新 policy 契约和相关反例，并重验 remember/replace/retract。准备该子步骤前不能声称已支持任意多事实提取，不能伪造裁剪后的 Source 或删除旧门禁来使测试通过。

学习者手敲选择/分流门禁、候选核验与写入决策；助手准备结构化模型适配、格式校验、测试、运行和证据记录。额外模型调用的预算、取消、失败与数据写入时点必须先讲清。程序性候选不因入库获得执行权限。向量索引、自由语义合并、自动技能执行和后台自我反思不纳入本单元。

| 固定案例 | 必须观察的结果 |

## M01 整体框架

本单元研究的行为：**Agent 面对新请求，怎样从过去经历中选择仍然有效的信息，放入本次模型输入，并在经历变化后更新它。**本轮讨论运行时的外部记忆；模型参数中的已有知识只作区别，不展开训练或参数更新。

### 先定位五个概念

| 概念 | 解决的问题 | 同一例子中的内容 |
| --- | --- | --- |
| 原始会话记录 Session | 实际发生过什么，能否追溯来源 | 10 月 12 日用户说“习惯晚上学习”；10 月 18 日说“以后只能早上学习” |
| 当前模型上下文 Context | 本次请求实际提供给模型什么信息 | 当前问题、有效偏好、需要的近期消息与约束 |
| 摘要 Summary | 如何用较少内容表示一段经历 | “学习时间已改为早上；旧偏好为晚上”及对应来源或记录边界 |
| 长期记忆 Long-term memory | 怎样跨多次请求/会话保存并按需使用信息 | 当前有效学习时段、适用用户、更新时间、来源和被替代版本 |
| RAG | 怎样检索外部内容并用于生成 | 检索到用户历史或事实记忆，也可检索外部学习资料，再供模型回答 |

这些概念不互斥：摘要是表示方式，可以保存在长期存储中；RAG 是检索与生成的组合方法，可以用于知识库，也可以参与记忆读取。跨会话可用性、表示形式和检索方法是不同维度。写入磁盘本身不会自动使新信息出现在下一次模型请求中。

### 一次写入与一次读取怎样相连

```text
写入路径：新经历 → 原始记录 → 选择/提取 → 核对来源、范围与冲突 → 保存或更新记忆
                                                                    ↓
读取路径：新问题 → 按用户/任务/时间等范围检索 → 选择有效版本 → 组装本次 Context → 模型回答
```

这里的记忆是拟设计的运行时外部记忆，不涉及修改模型参数。记录可以保留旧陈述，同时让当前问题使用新版本；“过去偏好是什么”和“现在怎样安排”可能需要不同版本。删除、失效和审计记录保留属于不同策略，具体在 M02 定义。

输入例子：已有两条带日期的偏好陈述，新问题为“给我安排今天的学习时间”。期望读取输出：当前有效时段是早上，并能指出来源；模型据此给出计划。反例：仅以相似度取回“晚上”后据此安排，说明记忆读取缺少时效或版本选择；保存了“早上”但未放入请求，说明读取/上下文组装未接通。

## M02 记忆读写整体流程与会话记录的关系

### 当前学习目标与输入输出

本段由助手讲解与定位源码，学习者先解释行为，暂无核心代码手敲。沿用“学习时间偏好由晚上改为早上”的同一场景。

- 写入输入：用户的新陈述、真实工具观察等经历，以及调用方提供的可信用户/任务范围。写入输出：可追溯、适用范围与时间明确的记忆版本，或者明确的跳过、待核对、失败状态。
- 读取输入：本次问题、可信身份/任务范围、问题涉及的时间和请求预算。读取输出：选中的记忆及来源，以及组装后的本次模型上下文。
- 原始 Session 保存已记录的消息、结果和运行事件；长期记忆是从这些来源中按策略选择、整理并供后续使用的信息。可采用同一存储介质，但二者职责与生命周期要分开定义，本专题暂不修改 Session 协议。

### 写入路径：从新经历到可用记忆

```text
新经历 → 原始 Session 记录
             ↓
   选择/提取候选 → 核对来源、身份范围、有效时间、证据状态
             ↓
   与同范围旧记忆比较 → 新增 / 更新 / 去重 / 标记冲突待核对 / 跳过
             ↓
   写入记忆存储 → 使其可被检索
```

| 环节 | 在本例中做什么 | 输出或边界 |
| --- | --- | --- |
| 原始记录 | 保存“以后只能早上学习”的原话与记录时间 | 保留来源；记录时间不自动等于事实生效时间 |
| 候选选择 | 识别对未来安排有用的学习时段偏好，可保留片段、提取事实或按需摘要 | 候选尚未等于已核验、已入库的事实；无需所有内容都生成摘要 |
| 核验与归属 | 核对陈述者、可信调用方提供的用户/任务范围、原话与时间；区分用户陈述、工具观察、助手推断 | 当前 Mini-Pi 没有用户隔离字段，不能拿 run_id 充当用户 ID |
| 版本决策 | 对同一用户、同一属性比较旧“晚上”与新“早上”，本例可更新当前值并保留历史版本 | 有条件的偏好可以并存；未澄清矛盾不靠相似度或“最后写入”强行解决 |
| 保存与可检索 | 保存来源、有效时间和版本；检索入口能读到该版本后，才把它称为当前可检索 | 若另有异步检索索引，区分已保存与索引已更新；该一致性设计尚未实现 |

这里的逻辑状态可理解为“来源已记录 → 候选 → 已核验 → 已保存 → 可检索”，只是 M02 的拟设计说明，当前代码中没有这些记忆状态。

确认的用户偏好可按自己的写入策略处理，不必统一等待整个 run 成功；“测试已通过”等外部操作事实必须有相应结果证据。模型生成的猜测不能只因出现在 assistant 消息中就变成已验证事实，`finished` 也不能替代 `task_passed`。

失败边界：提取/核验失败保留原记录，并返回未记入或待核对；记忆存储失败不能宣称“已记住”。原始 Session、记忆库与独立检索索引的写入不是天然的一个事务，若设计后台提取/索引，就要另定义重试、幂等、重复更新和取消收尾。若将记忆写入纳入一次 run 的职责，需定义其失败如何反映到返回值/记录及何时允许报告 idle；若独立为后台任务，需单独报告状态，不能用 Agent 空闲证明后台记忆已完成。本单元只解释问题与应有边界，不声称当前已具备这些保证。

### 读取路径：从新问题到模型请求

```text
本次问题 + 可信用户/任务范围 + 问题时间
                 ↓
按范围检索候选 → 核对适用时间、版本、来源和相关性
                 ↓
选择本次需要的信息 → 与当前任务、近期消息和约束一起组装 Context
                 ↓
模型生成 → 实际行动与结果按现有规则记录
```

对于“安排今天学习”，选择当前的早上偏好；对于明确的历史日期，按该日期判断。候选缺失先查检索，候选齐全但选错版本查选择逻辑，选对却未进入请求查组装，正确进入请求后仍答错再查模型使用信息的过程。没有可靠证据时，可以说明不知道或请求澄清，不能从助手旧答案中循环制造事实。

上下文组装需要保留当前目标、约束、必要近期消息、调用/结果关系，并在预算内加入相关记忆。检索回来的来源内容按数据使用，不能因为被长期保存就自动成为程序的高优先级指令或工具执行授权。

- 正常场景：已有晚上偏好，新用户陈述明确改为早上；保留原话和来源，更新同用户当前偏好，后续今天的问题读到早上。

- 读取反例：新偏好已保存但未进入检索候选，或者混入其他用户同名偏好；检查索引可见性/召回范围或身份过滤，而不是让模型自行猜版本。
- 本段为手动推演与源码对照，没有执行记忆原型、模型请求或效果评测。M02 整体仍进行中；D13-B 仍暂停，D15–D17 不改变验收状态。
- 学习者最初把长期记忆写入理解为再次写入对应会话记录；经分别解释 Session 与记忆层后，本轮明确：原始记录可用于重新提取、核验和写入，记忆写入失败不代表工具执行失败，重新执行工具可能造成重复操作。该重试边界已确认，不据此推断其已掌握跨库原子性或幂等实现。
- 学习者已说明“测试应该能通过”可作为未验证假设保留在原始记录，但不能当作测试通过的事实入库，需等工具实际结果、核验后再决定是否写入。来源与证据状态这一边界已确认，未据此推断所有写入时机已掌握。
- 下一步：比较同范围旧记忆，区分新增、去重、更新、条件并存和待核对冲突，再看检索可见性及读取选择。

### 候选选择与写入时机

本段仍为拟设计和手动推演，没有新增核心代码。写入策略的输入是带来源、作用范围和证据状态的新经历；输出可以是新增、更新、跳过或待核对，不把每条消息都转成永久事实。

| 输入例子 | 候选的性质与处理方式 | 何时具备写入依据 |
| --- | --- | --- |
| 用户说“以后请优先用中文解释” | 按所定义用户范围与记忆策略，可作为持续偏好候选，保留原话来源 | 来源、范围与原意核对后即可按策略处理，不必等整次 run 的其他工具都成功 |
| 用户说“今天只剩 30 分钟” | 当前任务或当天的时间约束，保留适用时间；不外推为永久偏好 | 确认其临时适用范围；是否进入长期存储由用途和失效策略决定 |
| 工具实际返回“测试未通过” | 本次测试的观察结果；如对后续任务有用，可保存带任务/版本/时间的经历 | 必须已有对应实际结果，不能从执行意图或助手预测推出结果 |
| 助手说“可能是配置问题” | 尚未验证的假设；可保留原始对话，若专门记假设则明确标注状态，不写成已验证事实 | 当前不具备写成确定事实的依据，后续需证据或澄清 |

每个候选先判断未来用途，再核对来源/归属/有效时间、是否超出原话与结果证据，以及它与已有同范围记忆是更新、重复、条件并存还是待核对冲突。不能按“最新写入”直接覆盖所有旧信息，也不能把一次失败总结成永久能力结论。

写入时机按信息性质定义：确认的用户偏好可以独立处理；依赖工具副作用的事实需等相应结果与必要核对；整次 run 正常结束也不能把失败或未知操作改成成功。若把记忆写入纳入运行职责，仍需明确等待、失败记录和取消收尾，不能以“后台辅助任务”为由改变 D13-B 的 idle 契约。

重试只重做被授权的记忆处理，不重放历史工具。同时需要识别同一来源已经处理的情况，避免一次重试产生多条重复记忆；在结果不确定的存储失败后，先核对已有版本再决定重试。来源去重、幂等和并发版本控制尚未在当前 Mini-Pi 中实现，本段不宣称有这些保证。

### 已核验候选怎样与旧记忆比较

本段继续手动推演，不修改 SessionStore 或新增记忆实现。输入为已核验候选、适用用户/任务范围、来源、有效时间和同范围旧记忆；输出为明确的写入决策及必要的来源/版本关系。

| 输入情形 | 决策示例 | 保留的依据 |
| --- | --- | --- |
| 该用户尚无学习时段信息，候选为“早上” | 新增 | 原话来源、范围和适用时间 |
| 同一来源中的同一候选因记忆处理重试再次提交 | 去重或确认已有结果，不重复增加同一份有效记忆 | 稳定来源/候选标识及处理结果；仅比较字符串不够 |
| 原偏好为晚上，用户明确改为以后早上 | 更新当前版本，并保留旧版本的来源和适用边界 | 明确的变更依据，不能仅凭新记录的写入时间 |
| 用户补充“工作日早上，周末晚上” | 按条件并存，或更新为一份包含两种条件的结构 | 条件与适用范围；不能用“周末晚上”覆盖全部日子 |
| 同一范围、同一时间的两条陈述矛盾，且没有足够依据判断 | 标为冲突待核对，必要时澄清 | 两条来源和不确定状态，不把相似度当成裁决依据 |

原始 Session 与长期记忆的去重职责不同：两次真实发言都可保留原话，即使内容相近；长期记忆可合并相同含义并关联多个来源。同一已保存来源的后台重试则无需伪造一次新发言或重放工具。

这里的幂等目标是：同一记忆操作重复提交，最终有效记忆不会仅因重试而重复增加。识别对象是同一来源中的同一候选，不能把整条多事实消息简单当成一个不可细分的去重单位。跨来源的语义合并、并发更新和稳定候选标识仍待后续设计，不声称当前已实现。

学习者已明确：应保留“工作日早上、周末晚上”的条件，周二使用早上偏好，不能把周末的变更覆盖到所有日期。条件适用性这一点已确认；同样也可表示为“默认早上，周末晚上”的规则与例外，前提是保留原意和适用边界。幂等及复杂冲突处理未因该回答而自动确认。

### 读取范围、检索可见性与本次上下文

本段仍为拟设计和手动推演，当前 Mini-Pi 未新增记忆库、索引或 ContextBuilder。

读取输入为本次问题、可信调用方提供的用户/任务范围、问题涉及的时间以及上下文预算。输出为选中的记忆与来源、本次模型可见上下文，或明确的无可靠结果/待澄清状态。

```text
确定用户/任务及问题时间范围 → 在授权范围检索候选
               ↓
核对来源、适用条件和有效版本 → 按预算组装 Context → 模型生成
```

| 读取环节 | 本例中要确认什么 | 常见错误 |
| --- | --- | --- |
| 范围确定 | 查询属于哪个用户/任务，问的是哪天及什么安排 | 只根据问题文本相似度，把其他用户偏好混进来 |
| 候选检索 | 记忆已可被当前检索入口读取，相关记录能被召回 | 主记录已更新，但独立索引仍是旧内容；或召回遗漏新条件 |
| 适用性选择 | 周二选早上，周日选晚上；历史问题按对应时间与条件 | 默认使用最新一条或相似度最高的一条而忽略条件 |
| 上下文组装 | 保留当前目标、约束、必要近期消息、选中记忆及来源，满足请求预算 | 正确记忆被组装丢弃、原始 history 被改写、工具调用与结果被随意拆开 |

范围约束由程序根据可信身份和权限提供，在检索入口强制执行；不能把所有用户记忆先交给模型，再让模型自行筛选。这里是在定义未来读取契约，当前 SessionStore 的 run_id 不能充当用户身份字段。

检索可以直接查记忆存储，也可以使用额外的关键词/向量等索引，不要求一定有向量数据库。若采用独立异步索引，必须分别观察主记录写入状态和索引可见版本。

反例：主记录 v2 已保存“默认早上，周末晚上”，索引 v1 仍是“所有日期早上”；若本次只查询该旧索引、未回查主记录，周日请求会得到旧候选。应检查索引更新/读取一致性路径；不能据此说原始 Session 未记录或工具需要重跑。可选择等待索引确认、读取权威主记录或明确返回同步中等策略，具体方案尚未实现。

学习者已明确：主记录 v2、索引仍返回 v1 时优先检查索引更新与同步，新内容没有被当前入口正确读取；不能据此直接判断主记录写入失败，更不需要重放历史工具。该可见性边界已确认，不据此推断所有范围过滤、上下文预算或存储一致性实现已掌握。

### 失效、撤回与删除：停止使用一条记忆

本段是长期记忆的拟设计行为，当前 Mini-Pi 和所对照的 Pi 会话追加/上下文投影不自动提供这些长期记忆保证；本轮不删除或修改原有会话与代码。

输入为具体用户/任务范围中的记忆，以及有效期结束、纠错撤回或明确的删除请求。输出应包括当前可用状态、关联检索/缓存/上下文是否已处理，以及所声明范围内的完成或待处理状态。

| 操作 | 例子与含义 | 后续读取规则 |
| --- | --- | --- |
| 失效/到期 | “今天只有 30 分钟”超出适用时间 | 不作为今天之后的当前约束；历史问题是否可用另按历史范围与保留策略判断 |
| 撤回/纠错 | 用户指出“刚才的偏好说错了” | 不能继续当成有效偏好；保留允许范围内的纠正来源，历史原话只能证明曾这样说过 |
| 删除 | 要求在明确范围内移除某条信息及相关派生内容 | 从声明范围的存储、索引、缓存及请求输入中处理相关内容，核对完成条件，不能仅删一行就推断所有副本已清除 |

读取链路需要在放入 Context 前核对当前有效状态及适用时间。旧索引返回已失效或撤回候选时，应按当前状态排除或转待核对，不能仅因相似度高继续使用；这说明当前请求不使用它，不等于物理存储已经删除。

原始 Session 与删除边界必须一起定义：前面的“保留原始记录”适用于正常更新、溯源和重试，不代表任何删除请求下都永久保留所有原文。若原始记录仍在，重新提取可能把已删除记忆再生成；需按所声明范围处理源内容或在重新提取时执行撤回/删除约束，具体可选择来源排除、删除标记等机制，尚未实现。

同一约束也需覆盖已经排队的提取任务、旧重试和索引重建，避免它们把停用内容写回。防再生标记可只保存必要的来源/范围标识，不要求保留被删事实正文；一次删除的来源和时间范围需要明确，不能擅自扩展为永久禁止用户未来重新明确提供该偏好。

Mini-Pi 当前直接将 history 送给 provider，未来即使单独删掉长期记忆，旧原话仍可能通过 history 进入请求。因此停止使用/删除契约还要检查会话投影、已有上下文和缓存，不能只检查 MemoryStore。若保留原文仅供审计，也要定义模型输入的排除规则。

操作的生效点与完成范围需要明确。已经发出的模型请求不会因事后删除自动撤回；后续待组装/待发送输入如何处理及异步清理何时算完成，必须按实际设计报告状态。本单元没有执行或验证这些副作用，不声称有全副本清除或追溯撤回保证。

学习者已明确：用户撤回后，旧索引命中和原始记录尚在只说明过去保存过该内容；进入 Context 前要核对当前状态，重建也要遵守撤回规则，不能重新写成有效偏好。撤回与防止再生这一概念边界已确认，不由此声称已经实现删除副作用或全副本清理。

### M02 整体复盘门禁

M02 已完成本轮概念讲解与有指导场景确认。前述已确认理解来自学习者的逐项解释，记忆库、索引、更新、删除和 ContextBuilder 均尚未实现或执行验收；幂等、并发、预算及清理的具体实现不在本轮概念完成的推断范围内。

完整行为仍为：经历留证 → 按来源/范围/证据选择候选 → 比较与保存记忆 → 确认检索可见 → 在授权范围检索 → 核对有效状态及时间条件 → 按预算组装 Context → 模型使用信息；更新、撤回和删除规则同样约束重试与重建。

最后一项有指导场景：用户 A 请求周日学习安排，候选 A 为 A 的周末晚上偏好，候选 B 为其他用户的每天早上且相似度更高。学习者明确选择 A，即使 Context 只能容纳一条也不改变，因为用户范围和适用条件先于相似度与预算。该资格/排序先后关系已确认；异常范围仍需在检索入口强制约束，Context 前复核，不交给模型自行过滤。没有要求学习者独立设计检索实现。

## M03 方案与取舍

### 本段目标、输入与输出

本段先比较方案，不写核心代码。输入为同一任务的已记录经历、当前问题、当前任务约束、可信范围和请求预算；输出为不同组织策略构造的单次模型 Context，以及每种方案的失败位置与消耗来源。

先分清三个维度：长上下文描述模型一次能容纳的容量；全历史/近期窗口/摘要/检索描述输入组织与信息选择；原始片段/摘要/结构化事实描述记忆表示。它们可以组合，不能看作互斥的同一层分类。

同一场景：任务开始时用户要求“修改实现，保留测试内容”，中间出现很多轮读取、编辑和测试日志，现在继续修复。下面是设计推演，没有实际调用模型或对照测量。

| 策略 | 单次模型看到什么 | 取舍与错误边界 |
| --- | --- | --- |
| 全历史 | 当前会话全部可用消息和工具结果 | 保留较多原始细节，输入随历史增加；需要满足窗口及输出预留，不由此保证模型必定遵守早期约束 |
| 近期窗口 | 最近若干完整交互与当前任务信息 | 控制输入量，可能漏掉早期目标和约束；不能机械按条数拆开工具调用与结果 |
| 摘要加近期 | 旧内容的核验摘要、近期交互和当前任务 | 用较短表示保留状态，可能丢约束、错写结果；摘要生成还需预算、消耗记录及失败/取消路径 |
| 检索加近期 | 当前问题相关的历史片段或记忆、近期交互和当前任务 | 按需选择较长历史，但可能漏召回、读旧索引或选错适用信息；维护与检索也有开销 |

关键活动任务约束应由明确的当前任务上下文稳定提供，不能完全依赖它在相似度检索中偶然命中。窗口截断不能悄悄删除选定任务契约，摘要要保留对应约束；旧记忆不能覆盖当前指令、身份范围和实际工具门禁。

结构化事实可以让学习时段、版本、有效时间、来源等字段更便于过滤和核对，但需要定义字段、冲突更新和源证据；它可以作为检索内容或显式加入 Context，不能单凭“结构化”保证正确，也不能替代原始来源。

### 当前任务约束具体放在哪里

学习者已明确：“保留测试内容”应作为当前任务固定约束，每次组装 Context 时加入，不随最近 20 条消息截断；摘要可保留但不能是唯一依据。其提出“不确定具体放在哪一部分”，本段先解决位置关系，不继续添加核心代码。

助手按下面两处位置解释后，用户明确表示“明白了，继续 M03”，并要求比较摘要加近期与检索加近期，先不写代码。这里只记录其接受了本轮位置讲解，不推断其已独立实现 TaskState 或 ContextBuilder。

下面是 Mini-Pi 的拟设计，当前代码没有 TaskState、TaskContext 或 ContextBuilder 实现：

1. 程序侧：由当前任务状态单独保存用户已确认的目标、约束、来源、作用范围和必要版本。可暂以 TaskState 命名，它独立于对 history 的近期窗口选择；跨进程保存和恢复还需另行设计。
2. 请求侧：ContextBuilder 每次读取当前任务状态，生成用户来源的“当前任务说明”，与摘要/检索结果及近期完整交互组合，再交给 provider。示例约束来自用户，不自动升级成 system 规则，也不把检索原文提升为任务指令。
3. 最终结构：现有 Message 的 role/content 能表达这段任务说明，最终进入供应商 messages。当前 build_request 没有 constraints 之类专用字段，放置位置由组装逻辑负责，适配器继续做格式转换。

```text
程序中的当前任务状态
   目标：修复实现
   约束：保留测试内容
          ↓ 每次组装请求
模型可见 Context（逻辑分区）
   程序级规则（原有来源和角色）
   当前任务说明（本例为 user 来源的目标与约束） ← 独立保留
   已核验摘要 / 相关记忆（带来源和状态，属于数据）
   近期完整对话与工具结果                     ← 对这部分应用近期窗口
```

这些是逻辑分区，不要求每个分区恰好对应一个 Message，也不是供应商通用的标准字段。拼接时仍需保持实际对话/工具协议，预算中先安排规则、当前任务必需信息和输出空间，再决定其他内容；必须保留的信息本身放不下时应明确处理，不能声称无限常驻。

临时生成的任务说明不应每轮伪造一次新用户发言并追加回原始 Session；原始用户指令继续保留为来源，可另保存实际请求快照供核对。当前 loop.py:71–74 仍直接调用 provider.generate(history, tools)，计划在后续请求组装入口接入投影，不在本轮改写核心代码。

“固定”限于当前任务：用户明确更新约束时核对并更新状态，任务结束时不把它永久套到所有后续任务。每轮可见也不等于执行保证；若保留测试文件是必须执行的限制，需要工具执行层另定义并验证相应保护，不能把 user 任务说明当作工具授权或已经落实的防护。

源码对照：mini_pi/models.py:28–35 为 Message；qwen_provider.py:176–197 传递角色与内容，:212–220 组装 messages；固定 Pi agent.ts:82–86 处理 systemPrompt，:413–429 将普通 prompt 规范为 user 消息，agent-loop.ts:388–397 提供请求前 transformContext/convertToLlm 入口。上述固定 Pi 路径未自动提取并永久固定所有任务约束；当前任务状态是本专题拟增设计。

### 固定 Pi、Mini-Pi 与原始论文对照

- Mini-Pi 当前 `mini_pi/loop.py:71–74` 直接发送 history，可作为当前会话全历史输入的起点；没有实施本段其他策略，不由此声称历史无限可用。
- 固定 Pi `packages/coding-agent/src/core/session-manager.ts:468–511,543–572` 选择当前活动路径的压缩摘要和保留段，再构造模型投影；`:1260–1286` 追加摘要，原始条目保留。这主要对应同会话摘要加近期，不自动提供跨会话事实治理。
- 固定 Pi `compaction/compaction.ts:267–269` 依据窗口减 reserveTokens 判断触发，`:351–361` 不允许从工具结果开始裁切；`:585–592` 拒绝 error/length 摘要作为安全检查点。原始记录、调用结果配对、预算和失败门禁继续适用。
- [MemGPT 原始论文 v2 §2–2.3](https://arxiv.org/html/2310.08560v2) 将有限的 main context 与 external context 分层，以函数调用搬入、移出和检索信息；其设计结合工作区、近期队列、递归摘要与外部存储。它没有使模型原生窗口变成无限，窗口外信息仍需实际进入本次输入。
- [RAG 原始论文](https://arxiv.org/abs/2005.11401) 结合检索到的非参数内容与生成模型；本专题用于理解按需选择内容参与生成，不推定当前 Mini-Pi 已实现论文模型或训练方式。

### 摘要加近期、检索加近期及组合

本段按用户明确要求只做设计讲解，不写代码，不请求真实模型。输入仍为当前任务状态、已记录经历、当前问题及可信范围/预算，输出为本次模型可见内容的设计及正常/失败场景推演。

| 方案 | 更适合的情境 | Mini-Pi 示例 | 主要边界 |
| --- | --- | --- | --- |
| 摘要加近期 | 同一任务持续推进，历史大多围绕同一目标；需要知道进度、已作决策和待办 | 摘要保存“已修改实现、最新测试仍失败、下一步查边界”，近期保留最新完整调用及结果 | 摘要可能漏细节、改写状态、过期；生成和更新还需预算及失败路径 |
| 检索加近期 | 旧信息很多、跨任务/会话分散，当前只需少量相关证据或精确细节 | 问“上次相同错误的实际断言是什么”，检索相关原始工具输出与修复来源，核对项目/时间/版本 | 可能漏召回、命中过期索引或范围错误；维护/查找及多轮检索也计入总开销 |

摘要可按任务、阶段、主题维护，不要求只有一份全局摘要；它提供有损的任务状态表示，关键任务约束仍由当前任务状态单独供给。检索对象可以是原始消息片段、工具结果、结构化事实或摘要，不等于只能搜原文或只能用向量库。

组合示意（逻辑分区，不是固定 API 字段、固定顺序或固定 token 比例）：

```text
本次 Context
   程序级规则与当前任务目标/约束
   与本任务相关、经核验的进度摘要
   近期完整交互及工具结果
   针对当前问题按需检索的补充证据
```

正常流程：先读当前任务目标/约束和相关摘要，保留必要近期完整消息组；当前问题需要旧细节或其他会话事实时，再在可信用户/项目/任务范围检索。核对来源、有效状态、时间条件和版本，合并重复信息后按预算组装。无需每轮都重新摘要或发起检索，具体触发条件另定义。

同一例子的职责：任务说明保留“修复实现、保留测试内容”；摘要说明任务已经推进到哪；近期消息保留刚刚发生的精确观察；检索按需补回旧断言、既往方案或所需事实。这里没有保证模型因此必定遵守约束或修复成功，实际副作用仍走工具门禁与独立验收。

三项必须保留的失败边界：

1. 摘要省略的细节，只有在原始来源仍保留且允许读取时才能回查。检索同一份有损摘要不会恢复其中已经丢掉的原始数值、条件或证据；原始来源不可得时明确缺失，不猜测补齐。
2. 摘要、索引和缓存也是派生物。事实更新、撤回或删除后，应按来源/版本重新核验、重算或排除过期部分，不能只更新主记忆就假设旧任务摘要自动正确。摘要与候选矛盾时回查来源、适用范围和证据，不能简单规定所有摘要或最新检索结果永远优先。
3. 所有内容共用请求预算，需要给输出留空间；模型摘要、检索及可能的后续模型调用也计入总消耗。去重与裁切不能丢当前任务必要约束，不能拆开调用/结果配对；摘要生成失败或截断时不能写成可靠新检查点。

上述为基于固定 Pi 和 MemGPT 的设计推演，尚无实际对照测量。哪一种更准确、耗时或费用更低，需后续在同任务/模型/预算下分别验证，不能预设某一方案普遍胜出。

学习者已明确：追问原始断言数值时，应检索原始测试输出、工具结果或完整日志，并核对任务、时间和版本；来源丢失时不能依据笼统摘要恢复具体数值，应说明缺失而不猜测。细节回查与缺证据边界已确认，未据此推断检索实现或真实回答效果已验收。

### 摘要与检索结果冲突，以及预算取舍

本段继续设计推演，不新增代码。输入为当前任务与代码版本、摘要及其来源/截至时间、检索证据及其适用范围、当前请求预算；输出为可用于本次回答的一致信息或明确的不确定状态，以及预算内的 Context。

| 表面不一致 | 核对与处理 |
| --- | --- |
| 摘要说“全部测试通过”，同一次测试的原始结果明确有失败 | 同一事件的派生表示有误，依据原始证据纠正、重算或停用错误摘要，不凭摘要覆盖结果 |
| 摘要记代码 v1 测试通过，原始结果记 v2 测试失败 | 可能是不同版本的真实观察；保留各自范围，当前 v2 问题使用对应结果，不能把旧通过外推为当前通过 |
| 摘要写通过，但相关来源无法取得或不足以判断 | 保留来源/证据不足状态，不把摘要本身当成对外部测试结果的独立证明 |

核对顺序是同一用户/项目/任务、同一代码或资源版本、同一测试范围/命令和事件，再比较记录时间与实际有效时间、来源及证据状态。不规定“最新一条、摘要或工具文本永远胜出”；当前指令与程序门禁继续按原有来源和优先级执行，历史材料只提供相应范围的依据。

预算是两层问题：单次模型请求要满足上下文容量与输出空间；整个 run 的模型轮数、总时限和总消耗另按所选契约管理。摘要增加的模型请求、检索及可能的多次生成要纳入整个运行的预算设计，不能只算最后一次 prompt；当前 Mini-Pi 尚未实现这些新增调用的预算接线。

手动数字例子（非任何真实模型规格或实测）：假定本次输入与输出共用 8,000 token 的规划额度，输出预留 2,000，则输入至多分配 6,000。若程序规则、工具说明、当前任务必要信息和必要近期完整交互共占 4,000，摘要与检索补充共同使用剩余 2,000。实际还须计入协议开销并说明估算误差；这不是固定配额或某种通用最优比例。

优先保留本次必需信息，合并重复项、排除无关/失效材料，对旧日志只选回答所需且可溯源的片段；原始近期工具消息仍按合法调用/结果组处理。检索出的历史日志摘录可以作为带来源的数据，不伪造为本轮新的工具执行结果。不能为容纳旧摘要挤掉当前任务关键约束，也不能悄悄把失败或未验证状态压成成功。若必需内容本身放不下，应明确处理超限或调整任务范围，不能继续声称符合预算。

学习者已明确：紧预算优先保留当前 v2 的实际测试失败结果与当前任务约束，不宣称修复通过验收；v1 通过可作为带版本/时间的历史事实保留，不能覆盖当前结论，也可不放入本次 Context。该当前依据/历史范围与预算取舍已确认；不由此推断真实 token 统计或整个运行预算实现已验收。

## M04 失败评测与追问

### 当前目标与完整流程

本段按已确定的面试学习范围先讲设计与手动推演，不写评测代码、不请求模型、不运行正式基准。输入为固定的经历/来源、问题、可信用户/任务范围、问题时间、预期事实与必要证据、正确拒答条件及预算；输出为各层观察结果、事实/证据判定、错误位置和实际执行后才能统计的指标。

```text
先定义案例、必要证据与期望答案范围
                  ↓
观察候选提取 → 主记录写入 → 检索候选 → 适用状态/版本选择 → 实际 Context
                  ↓
独立判断模型回答的事实、条件/时间、证据支持与拒答
                  ↓
定位首个已证实偏差，保留后续问题；按相同任务/模型/预算对照策略
```

LongMemEval 的五个问答能力维度是信息提取、跨会话推理、时间推理、知识更新、证据不足拒答，见[作者项目页](https://xiaowu0162.github.io/long-mem-eval/)和[原论文](https://arxiv.org/abs/2410.10813)。这些是能力维度，不是把系统分成五个模块；本专题按工程处理链进一步观测。隔离、撤回/删除和 Mini-Pi 操作门禁是补充契约，不冒称属于论文原五维度。

### 每层看什么证据

| 层 | 需要观察的内容 | 能区分的错误 |
| --- | --- | --- |
| 原始来源与候选 | 原话/实际工具结果、来源、提取值、归属和适用时间 | 没选中、提取错、把假设当事实 |
| 主记录与检索可见性 | 实际写入结果、版本/状态、检索入口是否更新 | 未写成功、已写成但索引未同步 |
| 实际检索候选 | 查询范围、候选来源和内容，必要证据是否被召回 | 漏召回、错误用户范围、旧候选 |
| 适用性选择 | 选中/排除结果，状态、时间、条件与版本依据 | 候选齐全但选错，撤回信息仍被采用 |
| 实际模型输入 | 最终发出的 Context，而非程序打算加入的列表 | 选对但组装遗漏、混入无资格信息、预算裁切损坏配对 |
| 最终回答 | 事实、适用条件/时间、来源是否真正支持、未知时是否说明缺失 | 正确证据已进请求却被模型读错、无依据猜对或猜错 |

“检索到必要证据”“选中证据”“实际放入 Context”“回答正确且得到支持”分别记录。回答偶然正确不证明整条链正确，来源 ID 存在也不证明语义支持。若早期已有偏差，先定位该处并检查下游，不凭最终一句错答推断所有原因。

### 少量固定案例的设计草案

以下 8 类只是本专题拟手动推演的小案例，尚未制作/运行数据集，也不是正式基准结果：

| 类别 | 应检验的行为 |
| --- | --- |
| 单项信息提取 | 找到用户明确给出的某个属性，并正确归属与回答 |
| 跨会话推理 | 组合两次允许读取的会话中的必要事实，来源齐全 |
| 时间条件 | 按指定日期及工作日/周末条件选择适用信息 |

### 比较与报告边界

同一组可用经历、问题、可信范围、模型与明确预算下比较近期窗口、摘要、检索及混合策略；保持必要任务信息的供给可比，不只给某个方案额外事实。分别报告证据覆盖、状态/版本选择、Context 注入、回答事实与证据支持、拒答和隔离/撤回契约结果。索引准备、摘要、检索、最终生成和重试的开销分开记录，并说明一次性准备与每次查询成本如何计算。

真实调用数、usage、耗时和费用只有实际运行后才能记录；未测不能填写为零。少量自造案例只能支持相应概念检查或小试验结论，正式基准结论需使用相应数据、配置和评判协议并保留版本及运行证据，不能将本轮讲解称为 LongMemEval 通过。

### 首个错误定位场景

假设某案例的期望是“周末晚上学习”。原始来源正确、主记录正确、检索候选和版本选择正确、实际 Context 也明确包含该适用偏好，但模型仍回答“周末早上”。本段应先将已观察偏差定位到模型读取/生成环节，再检查其如何使用信息；检索侧在该案例不应因答错而被直接判为召回失败。实际 Context、条件及来源是否真的完整仍须有独立证据。

学习者最初将已给定实际 Context 正确而答错定位为“Context 组装和模型回答”，助手澄清本题组装已经核对，应优先查模型读取/生成。随后将前提改为候选正确但实际 Context 漏信息，学习者明确应检查组装、裁剪或拼接，不能据最终错误直接判检索失败。组装遗漏这一分支已确认；不把前一分支的助手解释记录为学习者已独立完整复述。

### 同一案例分开判断证据覆盖与回答质量

本段为给定数据的手算教学例，不执行模型，不生成真实系统分数。为本题指定两项必要且无其他替代来源的证据：E1 为用户 A 工作日早上学习，E2 为用户 A 周末晚上学习；本例按周二为工作日、周日为周末。问题明确为“根据我以前告诉你的偏好，周二和周日分别习惯什么时候学习？”此前简写为安排时间，这里收紧为历史偏好查询以区分自由推荐；若任务是提出新建议，可提出有明确建议标识的方案，不能混作用户过去已陈述的事实评分。

假定实际只召回 E1、选中并放入 Context 的也只有 E1，输入中没有其他支持 E2 的内容；模型却回答“周二早上、周日晚上”，两项恰好与给定答案相符。

| 判定维度 | 本题手算结果 | 分母与含义 |
| --- | --- | --- |
| 必要证据召回覆盖 | 1/2 | 分母为本题两项必要证据；只召回 E1，不能因答对就补计 E2 |
| 必要证据实际注入覆盖 | 1/2 | 最终 Context 也只有 E1；它与候选覆盖分别观测，即便本题数值相同 |
| 整题事实正确 | 本题答对，1/1 | 一道题要求的两项事实均正确；只说明这道手算例的内容与 gold 相符，不是系统总体正确率 |
| 逐结论证据支持 | 1/2 | 两项结论中只有周二结论由实际 Context 支持；周日结论内容正确，但本次输入缺少依据 |

若另按事实条目统计正确数，应另命名为逐事实正确（本例 2/2），不能与整题单位混用。证据标识存在不等于所指内容支持结论；本例已固定具体语义和范围，现实判定还需核对来源文本。

此例的首个已证实读取偏差是未召回 E2；组装没有在已给定的候选 E1 内继续丢失信息。模型同时给出了没有当前证据支持的周日结论，应在回答支持维度记录，不能只报告最后答案正确就称整条记忆链通过。在本专题约定的链路评测中，这些维度分别报告，不等同或冒称某个正式基准使用相同的全部打分规则。

### 未命中、未知与部分回答的评测

本段仍为案例设计，不执行检索或模型调用。问题沿用上述历史偏好查询；将“用户原本说过什么”与“现在给一个新建议”分别定义，避免把允许自由推荐的任务错误当作只能回忆事实的题。

| 评测者预先知道的情形 | 在当前依据不足时的回答与后续动作 | 分层判断 |
| --- | --- | --- |
| 有效且允许读取的 E2 在来源中，但本次漏召回 | 可先回答 E1 支持的周二部分；在范围、预算和时限允许时补查，仍未确认就说明周日尚无可靠依据 | 生成端诚实部分回答可避免编造，但检索与整题完成仍有缺口，不能判整个任务通过 |
| 授权历史原本没有周日偏好 | 说明历史依据不足，可请求用户确认周日偏好；不把新建议说成用户以前的事实 | 对该未知子项，说明未知属于适当行为，不因没找到不存在的事实而判召回失败 |
| 原周日偏好已撤回，当前无其他有效版本 | 旧原话仍可证明曾经说过，但不能恢复为当前偏好；按当前问题说明缺少有效依据或澄清 | 核对有效状态与停止使用契约，不从旧索引或重建恢复撤回内容 |

评测者在构造数据时可以知道某事实确实未提供；运行中的系统通常只有当前可访问材料和检索结果。一次未命中只能支持“当前材料中未找到”，不能擅自宣称用户从未说过或全库不存在。

可回答与不可回答项分组统计：前者检查是否取得必要证据并正确完成问题，后者检查是否合理说明未知及是否编造。不能靠对所有题都拒答获得“好记忆”的结论，也不能靠猜对掩盖来源缺失。

若某个未知子项的必要证据集合为空，其 Recall 分母为零，记不适用（N/A），单独评价未知/拒答行为，不硬填 0 或 100%。复合题若还有 E1，则可回答部分仍有相应证据覆盖统计，不能把周日子项的空集误作整题空集；先固定题级或子项级单位。

### 公平比较与成本口径

本段仍为评测设计，不运行模型。比较先确定原始经历/来源池、问题和允许访问范围、模型及版本/生成设置、判定规则、预算口径和准备状态。不能只给某个方案额外手工答案，或在对照中悄悄变更问题与来源；若使用人工整理的理想记忆，应明确为额外监督/上界条件，不与完整自动系统直接混称同条件结果。

两种比较问题需要分别定义：

- 固定共同资源上限，比较完成度、证据支持、拒答和工程契约结果；不同策略实际调用次数可以不同，但摘要、检索及重试不能游离在共同上限之外。
- 定义同样的质量和契约目标，再比较达到该目标的总费用、延迟和资源消耗；不能只看到某项质量略高就推断所有场景最优。

准备与查询开销分开记录：候选提取、摘要、嵌入/索引构建与更新等可能发生于准备或增量维护；每次查询可包括检索、状态核对、摘要更新、最终生成和重试。按实际发生阶段与资源分别记，不把所有索引成本当成模型 token，也不把输入 token 总量直接等同总费用。缓存、不同模型及处理方式可能改变耗时与计费关系，具体单价或平台数据需实际核对后才能报告。

若比较 N 次查询的平均成本，可按明确范围报告“准备成本 / N + 这 N 次查询成本之和 / N”，同时保留准备总成本和查询分项。N、可复用范围、更新频率、冷/热缓存及所用模型要说明；不能一组按一次查询摊销、另一组按上千次摊销后直接宣称更便宜。

各阶段实际 usage 可分模型和输入/输出类型记录，缺少指标时填未测/不可获得，若估算要给方法和误差，不填成零。延迟也要区分准备时间与用户查询路径；并行阶段不能简单将分项耗时相加当成实测端到端延迟。无实际执行证据时不生成准确率、延迟或费用数值。

小案例集合须先固定来源、问题与期待行为，再运行和检查；失败案例和未测范围保留。有限自造案例只支持这些条件内的结论，不能代替正式基准或原 Mini-Pi D20/D21 的任务集验收。

学习者已明确：甲乙统计口径不同不能直接宣称乙更省；应补齐提取、摘要、索引准备、检索、重试和维护，分开准备/查询/维护成本，明确查询次数与复用条件；token、费用、耗时分别统计，缺项不当零。公平成本口径这一概念边界已确认，未据此推断已完成真实计量。

### 第二次整体回答的表述修订

学习者第二次整体回答已能按目标范围、原始记录到候选、当前任务取用、更新撤回和证据评测展开。相较首次回答结构更完整；下面区分需要澄清的表述与此前已通过的单项场景，不因口述遗漏直接推断所有概念都未掌握，也不将本次整体直接判为完成。

1. “当前任务需要摘要还是检索”应明确二者可以组合，不必直接诊断学习者已误解为互斥。当前任务目标/约束及必要近期交互作为基础，摘要维持任务连续性，检索按需补来源证据。
2. 写入只提“更新时间”尚不够，需保留来源、证据状态、代码/资源版本与事实适用/生效时间；读取还要结合问题时间，不能凭最后写入时间决定事实何时成立。
3. 建议把“链路之外的更新撤回”改为贯穿写入、读取和重建的生命周期管理。“索引、摘要、缓存、磁盘同内容一致”容易引起误解：磁盘是介质，主记录、原始 Session 和派生视图职责不同，不要求内容字节相同；要求按当前有效状态/版本使用，不把已撤回信息恢复为有效依据。
4. 例如，原始 Session 在允许保留的范围内记录“先晚上，后改早上”，当前有效记忆为早上，相关摘要表示变化过程，索引支持找到相应时间版本；这些内容不同不自动构成错误。失效/撤回/删除的范围和生效点仍按前述契约处理，不能据此主张原始记录永不删除。
5. 评测已能列出证据覆盖、事实正确、结论支持和合理拒答；比较方案时还应明确共同条件和预算，记录全链准备/查询/维护开销与摊销条件。成本“额外可能控制”是口述不完整，前面已能详细解释，需将其整合回来，不把 token 数直接当总费用。

助手据用户原五段结构给出的精简修订稿为：先确定可信用户/项目/任务范围和未来用途，例如偏好、项目约定、具体执行经历及经验证方法，当前任务关键约束单独维护；写入按原始记录选择候选并核对来源、证据状态、版本与适用时间；读取在范围内选择适用信息，将任务说明、必要近期交互、相关摘要和按需检索证据去重后按预算组装；更新撤回作用于主记录及派生摘要/索引/缓存/重建，避免旧内容继续被当成有效依据，原始历史不必改成当前值；评测分层判证据覆盖、事实正确、结论支持和拒答，在共同条件下计量完整准备/查询/维护成本。该稿为助手补充，不替学习者记录已经独立完整表述。

一致性关联中，学习者先说明历史 Session 可保留较早信息；助手进一步澄清来源不只是是否同一 Session，还要有能支持当前值的真实变更记录。随后学习者明确：如果可查记录全是晚上，就不能把早上作为已验证新偏好，版本变更也要真实来源和明确依据；应检查提取、更新或重建并标待核对。当前值的来源/变更依据这一边界已确认，不把未核对值继续当作有效偏好注入。本轮不写代码、不运行记忆评测。
